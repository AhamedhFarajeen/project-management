Locally generated RSA keys and test session tokens exercised Clerk's actual token
verification middleware; no real Clerk account was involved. One scratch user was
linked to the test subject for these checks.

Each of these returned 401 without a token and 200 with a valid test token:

- GET /projects
- GET /tasks?projectId=1
- GET /users
- GET /teams
- GET /search?query=Design
- GET /tasks/user/1

Malformed tokens and tokens with an unauthorized frontend origin returned 401.
CORS returned the configured exact origin; OPTIONS /tasks returned 204 before auth.
Existing unit tests verify denied origins receive no CORS access header.

/users/me synchronization, initial account provisioning, sign-up, sign-in, sign-out,
and frontend redirects with a real Clerk session remain unverified end-to-end.
Their local unit tests pass, but the real Clerk instance must be configured next.
Authenticated users retain the existing shared-workspace access policy; team-based
isolation or role enforcement has not been added.

## Migration-related correction made during this review

The installed Clerk SDK automatically entered development keyless mode when keys
were absent. That can create a separate temporary frontend Clerk instance that the
Express backend does not share. Disabled it in client/next.config.mjs via
NEXT_PUBLIC_CLERK_KEYLESS_DISABLED=true. Both applications must now have explicit
keys from the same Clerk instance. Missing keys intentionally fail rather than
appearing to provide working authentication.

The SDK added /.clerk/ to client/.gitignore during the startup check; this protective
ignore rule was retained. The temporary keyless files generated by the check were
removed. No unrelated UI or business logic was changed.

## Seed defects confirmed

Fixtures insert explicit project/task IDs but do not advance PostgreSQL sequences.
Actual POST /projects and POST /tasks requests after a fresh seed failed with unique
constraint errors. The second seed run also fails because deletion order puts
parents before children and user/team fixtures depend on generated IDs. Exceptions
are swallowed, so a zero exit code does not establish success.

The first seed succeeds on a fresh database, and foreign keys enforce all seeded
relationships there. It is not a reliable reusable seed workflow. Do not run it
against real data. Repairing it requires a separate seed-specific change.
